# Languages (ES/EN)

Panoma speaks Spanish from birth and now English too, with no libraries: two flat
dictionaries and the compiler watching the keys. Spanish is still the **reference**
language — copy is written there first — but the **default** language is English: whoever
arrives with no cookie and no recognizable `Accept-Language` lands in English. Whoever
speaks Spanish says so in their header and lands in Spanish without touching a thing.

Seven tests watch over it: `apps/web/lib/locale-required.test.ts` (no component assumes the
language), `apps/web/lib/i18n-gaps.test.ts` (the holes a string declares are the ones
whoever paints it passes), `apps/web/lib/plurals.test.ts` and
`apps/web/lib/shape-holes.test.ts` (no inflected word glued to a figure),
`apps/web/lib/secrets-i18n.test.ts` (no scanner rule without its pair of keys),
`apps/web/app/api/model-language.test.ts` (no route pins a model's language on its own) and
`apps/site/docs/docs-copy.test.ts` (the only browser surface that **forbids**
Spanish).

## How it works

**Web** — everything lives in `apps/web/lib/i18n.ts`: two dictionaries of **1,423 keys each**,
`es` on lines 20-2133 and `en` on 2143-3794.

- `t(locale, key, holes?)` looks the key up in that language's dictionary. Holes go as
  `{n}` or `{name}` in the text and are filled from the third argument. **A hole with no
  value stays written just as it is** — `{n}` on screen — on purpose: that traces back to
  the dictionary, and a mutilated sentence does not.
- `getLocale()` resolves the request's language in Server Components: `panoma-lang` cookie
  → `Accept-Language` header → `"en"`. The layout calls it once and hands the result out:
  to the `lang` attribute of the `<html>` and to the `I18nProvider`.
- `localeFrom(request)` does the same for the API routes, which already have the `Request`
  in front of them and should not pay for the `new Function` this file uses to load
  `next/headers`. Thanks to that, an API's `error` and `hint` come out in the language of
  the screen — and a failure is exactly the moment you need to understand what it says.
- In client components, `useT()` (from `components/i18n-provider.tsx`) returns `t` with the
  language already applied; `useLocale()` gives the bare language (needed for `relativeDate`).
- The ES/EN switch at the foot of the sidebar writes the cookie (a year of life) and calls
  `router.refresh()`.

**The shape of the hole decides the plural.** `{s}` is filled by looking at `{n}`, `{ms}`
looks at `{m}`, `{totals}` looks at `{total}`; the shapes are `s`, `es`, `y`/`ies`. It is
resolved inside `t` and not at every call site because **the bug it fixes is one of
forgetting, not of arithmetic**: "1 commits", "1 carpetas sin control de versiones",
"1 signals detected" — the same one nine times over, and always because whoever wrote the
sentence did not remember that the number can come out as one. With fifty-two strings
affected, asking every site to pass `s: plural(n)` is asking somebody to remember fifty-two
times all over again.

**CLI** — speaks **English and only English** since 25-Aug-2026. It was bilingual with
`PANOMA_LANG` for a week and it was the one surface where the language got duplicated: the
web has a switch and a cookie, but a terminal inherits the system's language, so the same
person saw the web in one language and the terminal in another. `apps/cli/src/messages.ts`
keeps a dictionary and `say(key, vars)` reads it; the Spanish is in the git history.

## Adding a key

1. Write the Spanish text in the `es` dictionary of `apps/web/lib/i18n.ts`, in its
   surface's section. The key is `surface.name` ("`store.title`").
2. Add the English version in `en`. If it is missing, it does not compile: `MessageKey`
   comes out of the Spanish dictionary with `satisfies` and forces English to hold exactly
   the same ones.
3. Use it: `t("store.title")` from `useT()` on the client, `t(locale, "store.title")` on
   the server.

The English is not translated word for word: it is written the way a native product would
write it ("Espacio" → "Disk", "Apartados" → "Hidden"). If it sounds like a dictionary, it
is wrong.

## The landing page has its own dictionary

`apps/site/landing/landing-copy.ts`. It is a surface with its own root layout, its own
typefaces and not one key shared with the catalog. Its copy — seventeen groups of keys per
language, and a hundred and forty-three strings inside them — has no business fattening the
common dictionary. The mechanism is the same one — `getLocale()`, cookie and header — so
the language chosen in the app holds on the landing page too, and the other way round.

## `/docs` is the only monolingual browser surface

Three files in the repository state the opposite rule — `AGENTS.md`, [README.md](README.md)
and [doctrine.md](doctrine.md) — and all three say the same thing: **a person reads it in
the browser → bilingual**. `/docs` is the exception, it is written down in none of the
three, and it carries a test that enforces it.

`apps/site/docs/docs-copy.ts` is a **single dictionary, in English**, with no switch and no
`locale`: the page neither calls `getLocale()` nor receives a language. And
`docs-copy.test.ts:216-225` does not stop at leaving it untranslated: it sweeps every string
a visitor can read — `DOCS_COPY`, the command blocks and the navigation labels — and
**fails if a Spanish function word turns up**, with the pattern on its line 16:

```ts
const SPANISH_UI = /\b(el|la|de|para|qué|cómo|tú|catálogo)\b/i;
```

The defensible reason is that `/docs` is not product prose: it is the CLI reference, and
that same test checks that every verb, every flag, every memory cap and every MCP tool name
the page promises really does exist in the code. The reference for an interface that is only
ever typed in English, written in two languages, is two references that drift apart, and the
one that ages does not raise an error.

What **is** a measurable defect: `apps/site/app/layout.tsx:76` puts `<html lang={locale}>`
on both routes of the public site. The landing page needs it because it really is bilingual;
`/docs` is not, so a visitor with the browser in Spanish gets a page **in English declared
as `lang="es"`**. For a screen reader that is worse than saying nothing: it will read English
with Spanish pronunciation rules.

## The 401 is answered in two different languages depending on the format

`apps/web/middleware.ts:210-257`, the `unauthorized` function. When the port is open to the
network and the key is missing, it answers two things depending on the request's `accept`:

| format | language | who gets it |
| --- | --- | --- |
| JSON | English | a `curl`, the CLI — which prints it as is — and the MCP client |
| HTML | hardcoded Spanish | a person with a browser |

The top half is the house rule applied properly: `accept: text/html` separates the person
from the machine, and whoever gets the JSON is a machine. Until they were separated, all
three got Spanish — the MCP client included, which on top of that asks for English through
`Accept-Language` on purpose.

The bottom half is **debt, and today it is confessed only in a comment inside the file
itself** (`middleware.ts:205-208`). The page ships with `<html lang="es">` baked in and its
text written by hand. To be bilingual it would need the dictionary from `lib/i18n.ts`, and
nothing of Next can be rendered there: the layout queries the catalog, which is precisely
what this door refuses to show. The two texts would have to be carried over by hand — it
fits, and it has not been done.

## The words that travel to the API are not translated

An `action` in the body of a POST is **the order, not a label**. It stays as it is whatever
happens to the language of the screen, because changing it breaks every client that already
writes it — and the catalog has three kinds of client: the browser, the CLI and anything
that speaks HTTP.

Today those words are in Spanish, and there are thirteen of them:

| route | values |
| --- | --- |
| `POST /api/project` | `ocultar` · `mostrar` · `excluir` · `readmitir` |
| `PATCH /api/runs/[id]` | `aplicar` · `descartar` |
| `POST /api/ai` | seven, on the line below |

The seven for `/api/ai`: `usar`, `clave`, `olvidar`, `probar`, `entrar`, `entrar-estado` and
`modelos`.

This is not the general rule, it is what was left over: the newer routes already use English
verbs (`/api/notes` with `add`/`approve`/`discard`, `/api/assignments` with `withdraw`,
`/api/md/apply` with `init`/`sync`, `/api/agent/tasks/[id]` with `claim`/`complete`), and so
do the five values of `tool` in `/api/open` — `folder`, `editor`, `terminal`, `agent`, `app`.
**Mixed is wrong**; what cannot be done is fixing it with a plain rename, because there are
clients already sending all thirteen.

## The `id`s of `PROJECT_VIEWS` are still in Spanish

`apps/web/components/project-views.ts`. The ten view identifiers on the project page are
`all`, `resumen`, `actividad`, `retomar`, `cuentas`, `encargos`, `md`, `dependencias`,
`agentes` and `detalles`.

**They are not URLs: they are CSS marks.** The stylesheet switches views with
`[data-view="…"]` (`app/styles/project-panels.css:140-154`), so renaming an `id` forces a CSS
change and from the outside not one difference shows. What does show — the anchor that ends
up in the browser bar, gets pasted into a chat and saved as a bookmark — is in English and
comes first in each view's list: `#summary`, `#activity`, `#resume`, `#accounts`,
`#assignments`, `#md`, `#dependencies`, `#agents`, `#details`. The Spanish ones stay as
aliases and are not going anywhere: a link saved three months ago has to keep opening its
section.

## What is already settled, and what got settled along with it

This section used to be a to-do list in order of pain. It is not any more; what follows is
how each one ended up.

- **The whole interface is bilingual.** There is no screen, project page or cross-cutting
  page left untranslated, and what keeps it from happening again is not vigilance: it is
  that the parameter is mandatory. `locale-required.test.ts` forbids a default
  `locale = "es"` and `locale?: Locale` anywhere in `components/`. Twelve components carried
  it, and the task-status chips came out reading "abierta" and "en curso" embedded in
  English text on the very same card, with the English dictionary complete and right there,
  waiting for a parameter nobody was sending.
- **The strings that come out of the engine travel as a code and a number, never as a
  sentence.** `workRisks` returns `{ level, code, count }` and whoever paints decides the
  language with `riskText(translate, risk)`; the director's moves do the same with
  `moveText`, and with an explicit map instead of a `move.${code}` template, so that
  renaming a code breaks the build instead of leaving a blank hole at runtime. The secret
  scanner follows the same split by `ruleId`, and `secrets-i18n.test.ts` demands that every
  rule in `packages/core/src/secrets.ts` has its pair of keys.
- **What a model writes comes out in the language of whoever asked.** Until 25-Aug-2026,
  `/api/describe` and `/api/md/review` pinned "Escribes en español neutro" into the `system`
  without looking at anyone, and the worst of it was not the screen: **those two routes store
  their output**, so every day there was more Spanish written into the database that could no
  longer follow anybody. `model-language.test.ts` reads the arguments of every `complete(`
  — counting parentheses, not scanning the whole file — and fails if any of them pins the
  language without looking at the `locale`. The only one exempt is `/api/ai`, whose
  `complete()` is a heartbeat and not prose, and its reason is written down.
- **And what is already stored gets labeled instead of lying.** A paid call does not get
  redone: both writes record next to them which language they were written in
  (`decisions.ai_summary_lang` and `decisions.md_review_lang`), and the project page says so
  with `WrittenIn` when it does not match whoever is looking. Null means "written before this
  existed", and there the language is Spanish, because of how the prompt stood until that
  date.
- **The layout's `metadata` is computed per request**, because one of its fields has a
  language: the description is precisely the text that travels off the screen — the one that
  shows up when a link is shared and the one a reader announces before reading anything —
  and it came out in Spanish with the interface in English. The title does not need it:
  "Panoma" is the brand.

## What it does not do / known limits

- **`/docs` is not bilingual and declares itself `lang="es"` to a Spanish reader.** Both
  halves of the problem are told above; the first is a decision, the second is not.
- **The 401's HTML page is in hardcoded Spanish** and no test calls it out: it lives outside
  the reach of `locale-required.test.ts`, which only sweeps `components/`.
- **Thirteen API `action`s are in Spanish** and cannot be renamed without breaking clients.
  Nothing watches for a new route adding one more Spanish value.
- **`i18n-gaps.test.ts` checks that the holes match, not that the value is right.** Whether
  `{n}` gets the number it is owed cannot be read without running it. What it does prevent is
  what actually happened: "66 projects, looking in {donde}", where the text asked for
  `{donde}` and the component passed `where`.
- **The plurals only cover regular English and regular Spanish.** `SHAPES` knows about `s`,
  `es` and `y`/`ies`; the irregular ones carry their hole written into the text itself
  (`cop{ies}`, `repositor{y}`). A third language with more than two forms does not fit in
  this mechanism.
- **There is no dialect negotiation.** `Accept-Language` is walked in the order the browser
  sends it and the first tag beginning with `en` or `es` wins; the `q` values are not read
  and `es-ES` is not told apart from `es-419`. To choose between two languages, a `q` parser
  would be more code than judgment.
- **The comment on `getLocale()` says "En última instancia, español" and the code returns
  `"en"`.** The comment three lines further down does tell it right; the one in the header
  was left over from the previous version.
